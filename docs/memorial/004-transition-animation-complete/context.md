### 2026-08-19 — 诉求 1：过渡动画素材缺口调查（事实查证）

**素材比对结论（已脚本化精确比对，`assets/character/` vs 状态机定义）**：
- `assets/character/` 共 46 个 webp：10 循环态 + 36 过渡边。
- 10 循环态（idle/thinking/reading/replying/working/error/welcome/done/permission/listening）：**10/10 齐全**。
- 36 过渡边（`transition-{from}-{to}.webp`，见 `overlay-state-machine.ts:81-124`）：**36/36 齐全，缺口 0**。
- 孤儿文件（存在但不在 TRANSITION_EDGES 中）：**0**。
- 文件规模 2.4MB–7.3MB/个（过度帧 webp，非压缩状态）。
- 结论：**素材层面零缺口**，字符过渡动画素材已 100% 齐全。

**播放机制现状（`CharacterOverlay.tsx:317-328`）**：
- `<img src>` 播放 webp，过渡段用 `setTimeout(durationMs=800)` 推进（`DEFAULT_TRANSITION_DURATION_MS`）。
- webp 实际时长未知 → 800ms 是保守猜测，可能截断或空等（素材真实时长待核）。
- 宿主事件适配器（`createHostEventAdapter`）已实现但**未接线**：注释明确「后续工单订阅宿主事件时调用」。
- 状态机为**模块级单例**（`overlay-state-machine.ts:341`）：全局只有一个 currentState/playback，任何 dispatch 全局覆盖。

**多会话不适配根因（预判，待用户确认）**：单例 SM + 未接线的宿主事件 → 多会话并发时各会话的 thinking/replying 事件会互相覆盖，且浮层只有一个 img 一个 playback，无"焦点会话"概念。

### 2026-08-19 — 诉求 2：状态机重新设计（多会话适配）

**Q1**：多会话下状态机的组织形态？
**A1**：用户选「会话级 SM 实例 + 焦点仲裁」→ 每会话一个 SM（`Map<sessionId, SM>`），浮层只渲染焦点会话的 playback；焦点切换时跨会话过渡语义需重新定义。

**Q2**：焦点仲裁规则 —— 什么情况下焦点会话切换？
**A2**：用户答「以当前正在打开的会话为最优先」→ 焦点 = 用户当前打开/正在查看的会话；其他会话事件不抢焦。

**Q3**：非焦点会话的事件如何处理？
**A3**：用户选「更新各自 SM + 紧急事件抢焦」→ 非焦点事件照常驱动各自 SM，error/listening/permission 等紧急事件可抢焦浮层。

**Q4**：紧急事件抢焦后，何时交还焦点？
**A4**：用户选「事件消退即交还」→ 紧急事件结束后（该会话回到非紧急态）自动交还焦点给当前打开会话；期间用户手动切焦则保留手动焦点。

**事实查证（sub-task/001 已完成）**：
- 宿主信号全部按 sessionId 分区：`sessions.binding(id).session`（`ConversationSnapshot` 自带 `sessionId`）、`sessions.list`（`{ ids, byId, current, ... }`）；**不存在**全局单助手事件流，也不存在命名式 per-session 状态事件——状态需从快照差分推导。
- 焦点信号 = `sessions.list.getSnapshot().current` + `list.subscribe`（用户切会话即变）。
- 生命周期：`host/session-added` / `host/session-removed`（或 `ConversationSnapshot.removed`），`list.ids` 是会话集合事实来源。
- **本仓库已有 `session-follow.ts`**：只跟随 current 会话，`diffTarget` 差分推导（error > permission > working > replying > thinking > done > idle，reading 由 thinking 超时推导，done 驻留 4s 回 idle），经 `createHostEventAdapter` 驱动**单例** overlayStateMachine。→ 重新设计 = 把「单实例 + 只跟 current」重构为「每会话 SM + 焦点仲裁」，diffTarget 推导逻辑可复用为每会话推导器。

**Q5**：跨会话焦点切换时，浮层播什么过渡？
**A5**：用户选「直接切 + CSS 淡入淡出」→ 焦点切换不播状态机过渡，直接换到目标会话当前 loop，150ms opacity 过渡缓解跳变。

**Q6**：会话级 SM 实例的生命周期 —— 何时创建、何时回收？
**A6**：用户选「随 `list.ids` 同步」→ 会话出现在 `sessions.list.ids` 时创建实例 + 挂订阅，从 ids 移除时销毁并释放订阅。

**Q7**：紧急事件的精确范围？
**A7**：用户选「error + permission」→ 仅 `hasError`（error）与 `pending`（permission）可抢焦，与 diffTarget 推导源天然对齐；listening 无推导源、不纳入。

**Q8**：中间态表情（6 个）如何处置？
**A8**：用户选「保持端点 + 接入情绪反应」，并补充「不够素材可以再去弄，现有的素材尽可能使用上」→ 表情端点保留并活化（permission 情绪化、idle 低频点缀等），素材不足可新增。

**Q9**：过渡段播放时长机制怎么定？
**A9**：用户选「加载期解析 + 动态 durationMs」→ 素材加载时 ANMF 扫描精确填充 durationMs（零依赖 ~45 行，已验证可行），失败回退 800ms；导入素材自动适配。

**Q10**：表情活化的具体场景范围？
**A10**：用户选「仅现有素材覆盖的路径」→ (a) permission 情绪化（经 nod-smile/frown-wave）；(b) idle 低频随机点缀（idle→表情→idle，30–60s 一次）。**注：随后诉求 3 追加生活化表情，Q10 结论将被扩展（Q11 重新裁定）。**

**Q11**：生活化表情的清单与触发场景？
**A11**：用户选「三表情 + 事件触发」→ 新增开心/生气/惊吓三表情，各配事件触发：开心 = done 完成、生气 = error 出错；惊吓触发定义待定（Q12）。素材：每表情 `idle↔表情` 2 边 × 3 = 6 个新 webp；idle 随机点缀池混入新表情。

**事实查证（sub-task/002 已完成）**：
- webp 帧时长解析成功（手写 ANMF 解析，零依赖，46/46 全解析）：常规帧 67ms（≈14.9fps），过渡段末帧统一 536ms 收尾定格。
- 循环态（10 个）：75 帧 × 67ms = **5025ms/圈**，无限循环。
- 过渡段仅两档：45 帧型 **3484ms**（16 个）／75 帧型 **5494ms**（20 个）。
- **当前 `setTimeout(800)` 只覆盖真实时长 14.6%–23.0%** → 过渡动画实际被截断（播 12 帧就切走，536ms 定格永不出现）——这是「过渡动画完整做完」的关键缺陷。
- `durationMs` 字段已存在于 TransitionPlaybackItem（`?? DEFAULT`），可精确填充。
