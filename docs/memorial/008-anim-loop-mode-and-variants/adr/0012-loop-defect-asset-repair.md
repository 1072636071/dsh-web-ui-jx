# ADR-0012 — 循环缺陷的资产侧修复（倒放烘焙 + 局部镜像 + 降采样重编码）

## 状态

已接受（memorial 008 定案，实施中）。

## 背景

用户反馈部分循环动作「突兀」，且 working 态符咒「凭空出现」。逐帧取证（memorial 008 Q1）：

- 13 个循环态均为 `<img>` 播放 animated webp（`loops=0`），播完一圈末帧直接跳回首帧，播放器无倒放能力。
- happy/angry/surprised（mp4 转码而来）是**单向反应动作**：首尾帧差 20–27（严重不连续），且头部 0–4 帧残留源视频淡入（全局 alpha 86 vs 平台 122）。简单循环每圈「峰值姿态 + 满不透明」跳回「淡入暗帧」。
- working 循环体内符咒爆亮不对称：第 32–34 帧两帧 +130% 硬弹出，随后 ~10 帧软回落——每圈一次「凭空出现」。
- 10 经典态首尾缝 1.0–1.6（压缩噪声级），本质无缝；局部突变扫描确认其余态无物件 pop-in。
- 附带问题：3 表情素材各 32MB（150 帧、720×1280），而浮层显示仅 140×249（5 倍过采样）。

## 决策

1. **修复落在资产侧**：`tools/` 增加 Python/Pillow 循环修复脚本，双模式——
   - `pingpong`：裁掉头部淡入残留帧 + 裁掉尾部死定格，正放帧 + 倒放帧镜像烘焙进文件（对 happy/angry/surprised）；
   - `splice`：局部镜像——用爆亮回落段的时间反演合成「渐起段」，替换硬弹出（对 working）。整段倒放不适用 working（身体摇摆倒放观感怪异）。
2. **运行期零改动**：播放层保持 `<img>` + 零依赖（DESIGN.md §4），不引入 canvas/WASM 帧播放器。
3. **重编码策略**：修复资产一并降采样至 360×640（仍 2.5× 过采样）+ 高质量重编码；原素材备份至仓库根 `bak/`（加入 .gitignore，不进 git）。后续新素材沿用 360×640。
4. **素材规格沉淀**：单向动作素材必须烘焙倒放回程后方可作为循环态；全帧均值差对局部小物件突变不敏感，验收须叠加 block-max 扫描与目标色像素追踪。

## 被否决的替代

- **运行期帧播放器（canvas + WASM 解码，循环模式元数据）**：最灵活，但引入新解码依赖与常驻 CPU 开销，与「`<img>` + 零运行期依赖」架构冲突；为 4 个素材动大手术不值。
- **双素材 + 定时换 src**：正放/倒放各一份、按解析时长定时切换。src 重载有闪断风险、定时与帧边界漂移、资产翻倍。
- **保留 720×1280 仅重编码**：体积压不下来，烘焙后 git 负担继续加重。
- **全量素材一次瘦身**：收益大但超出本次范围，列为后续工单候选。

## 后果

- 素材规格新增「单向动作烘焙倒放」约定，后续同类素材入库前走同一脚本。
- 360 与 720 素材并存期：过渡段↔循环态切换处锐度差在 140px 显示下应不可感，验收确认；若可见，并入后续全量瘦身。
- `bak/` 保留原件，可随时回溯或按新策略重烘焙。
